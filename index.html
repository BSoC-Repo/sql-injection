Section 01

Introduction

Fortress Security Solutions sells security services — and its own customer login can be bypassed with one line of text. In this lesson you'll find out why, and fix it.

Learning objectives

By the end of this lesson you will be able to:

  • Explain what SQL injection is and name its root cause: mixing code and data in one string.
  • Point to the exact vulnerable lines in Fortress's login.php and explain how ' OR '1'='1' -- logs an attacker in as the administrator.
  • Rewrite the login query as a prepared statement using mysqli (and PDO).
  • Explain why binding parameters stops the attack, and apply the same fix to other queries — using an allow-list where a value can't be bound.
  • Name the supporting defences (least privilege, validation, safe errors) and explain why they come second.

Everything here is simulatedThere is no real database and no real credentials. The "database" is three made-up rows held in JavaScript in this page. Only ever test injection against systems you own or are authorised to test.

Section 02

What is SQL injection?

SQL injection happens when an application builds a database query by gluing user input into the SQL text. If that input contains SQL syntax — a quote, a keyword like OR, a comment marker like -- — the database can't tell where the programmer's code ends and the user's data begins. It simply parses the whole string as code.

Think of a receptionist who reads a form aloud as instructions: "Fetch the file for  name ." If a visitor writes "Smith — and also open the vault" in the blank, a receptionist who can't tell the form from the handwriting will do both.

The root cause in one sentenceCode (the query's structure) and data (what the user typed) travel together in one string, so data can rewrite code.

Concatenation  Fortress today

SELECT … WHERE username = '' OR '1'='1' -- ' AND …
one string, sent once
MySQL parser: "Quote closes the string… then OR… then a comment." The input became code.

Prepared statement  the fix

SELECT … WHERE username = ? AND …
channel 1: structure, compiled first
' OR '1'='1' --
channel 2: values, only ever data
MySQL: "Is there a user literally called ' OR '1'='1' -- ?" No. Login fails.

It's a bug as well as a hole

Concatenated queries also break for honest users. A customer named O'Brien types their own name, the apostrophe closes the string early, and the query fails with a syntax error. Prepared statements fix both problems at once.

Section 03

The vulnerability in Fortress

Here is the login handler as it ships today. The highlighted lines are the problem.

Spot the problem: lines 6–7 copy raw form input into $username and $password. Line 10 drops those variables (highlighted) straight inside the quotes of the SQL string, and line 11 sends the finished string to MySQL with mysqli_query(). Whatever the user types becomes part of the SQL.

Exploit walkthrough

  1. The attacker fills in the form

    FieldTyped value
    Username' OR '1'='1' -- (note the space after --)
    Passwordanything

  2. PHP pastes it into the query

    PHP doesn't know or care that the input contains quotes. It builds this string:

    SELECT * FROM users
WHERE username = '' OR '1'='1' -- ' AND password_hash = 'anything'
    • SQL code written by the developer
    • 'OR attacker's input running as code
    • -- ignored by MySQL (comment)

  3. MySQL parses the new structure

    • The attacker's first ' closes the username string, which is now empty: username = ''.
    • OR '1'='1' adds a second condition that is always true.
    • -- starts a comment, so MySQL ignores the rest of the line — including the entire password check.

    What MySQL actually runs is effectively:

  4. Every row matches

    How MySQL evaluates the WHERE clause for each row
    Rowusername = '''1' = '1'false OR true
    1 · adminfalsetrueTRUE — returned
    2 · j.smithfalsetrueTRUE — returned
    3 · a.patelfalsetrueTRUE — returned

  5. Authentication bypassed

    mysqli_num_rows($result) > 0 is true, so login.php fetches the first row — user 1, the administrator — stores its id in the session, and redirects to the dashboard. No password was ever checked.

    ImpactFull admin access with zero credentials. The same flaw in other queries can leak every customer record (UNION SELECT), change data, or, with the wrong database permissions, delete tables.

    The fix, step by step

     Apply the fix everywhere
    
    
    Fixing login.php is not enough. Search the whole codebase for mysqli_query(, ->query( and any SQL string containing $ or . concatenation. Every query that uses outside input — $_GET, $_POST, $_COOKIE, headers, even values read back from the database — gets the same treatment.
    
    
    
      
    
        
    Fortress pageVulnerablePreparedTypes
    
        
          
    Search"… WHERE name LIKE '%$term%'""… WHERE name LIKE ?"
    bind "%$term%" — wildcards go in the value    		"s"
    
          
    Registration"INSERT INTO users (username, email, password_hash) VALUES ('$u', '$e', '$h')""… VALUES (?, ?, ?)""sss"
    
          
    Profile update"UPDATE users SET email = '$email' WHERE id = $id""UPDATE users SET email = ? WHERE id = ?""si"
    
          
    Admin pages"DELETE FROM users WHERE id = " . $_GET['id']"DELETE FROM users WHERE id = ?""i"
    
            
      
    
    
    
    
    
      
    Numbers aren't safe eitherIn WHERE id = $id there are no quotes to break out of, so ?id=1 OR 1=1 works without any quote at all. Escaping functions can't help here. Binding with type "i" can.
    

    
    When a value can't be bound: use an allow-list
    
    
    Placeholders stand for values only. Table names, column names, and keywords such as ASC/DESC can't be bound. If the user picks a sort column, check it against a fixed list you control, and fall back to a safe default:
    
    
    
    The orange $sort / $dir are safe only because the allow-list guarantees they hold one of our own strings. Never interpolate a variable into SQL unless you can say that.

    Section 06
    
      Defence in depth
      
    
      Extra layers that limit the damage if something slips through. They support the fix. They don't replace it.
      
  
      
  
      
    
      
      
      Parameterised queries are the primary fixThey remove the cause. Everything in this table reduces the impact or catches mistakes. None of it makes concatenated SQL safe.
      
    
      
      
      
        
      LayerWhat it doesFortress example
      
        
          
      Least-privilege DB userThe web app connects as an account that can only do what the app needs. A successful injection can't DROP tables, read other databases or write files.GRANT SELECT, INSERT, UPDATE ON fortress.* TO 'fortress_app'@'localhost';
      Never connect as root.
      
          
      Input validation & allow-listsReject input that can't be valid before it reaches the database. Required for anything you can't bind, such as sort columns.preg_match('/^[A-Za-z0-9._-]{3,30}$/', $username)
      plus the ORDER BY allow-list above
      
          
      Safe error handlingLog detailed database errors privately and show users a generic message. Raw MySQL errors give attackers a map of your tables.mysqli_report(MYSQLI_REPORT_ERROR | MYSQLI_REPORT_STRICT); + try/catch → error_log(); display_errors = Off in production
      
              
      
      
    
      
    
      
      
      These are not fixes for SQL injection
        
        
          
      • addslashes(), or mysqli_real_escape_string() used as the main defence: easy to forget once, useless for unquoted numbers, and fragile with character sets.
        • 
          
      • Removing words like OR or SELECT: attackers just use other spellings, and you break legitimate input.
        • 
          
      • JavaScript validation in the browser: attackers send requests directly and skip it.
        • 
          
      • Hiding error messages: it makes attacks slower, not impossible ("blind" injection still works).

    Section 08
    
      Key takeaway
      
  
      
  
      
    
       Never build SQL by joining strings with user input
      
    
      Fortress's login was vulnerable because it concatenated user input into the SQL string, so data could become code. A prepared statement sends the structure first and the input separately as bound data, so no input can change what the query means.
